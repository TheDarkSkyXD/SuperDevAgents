### Autopilot-full

**You own the verdicts, never the PRs. One owner runs each PR from build to merge, and nothing merges without your clean swarm verdict.** For "autopilot this queue", "full autopilot", and one-owner-per-PR programs. Orchestrate runs a standing program whose coordinator lands verified work itself and whose workers never merge. Here each PR's owner carries the whole lifecycle through the merge, and the root keeps only verification, countersigns, and audits.

1. **Mark the operator's items and honor state-then-wait.** Items the operator names stay with the operator. The operator reviews and clicks, and no owner merges one. When the operator asks for the protocol or the plan to be stated, deliver the statement and stop. Execution starts only on the operator's explicit go. On that go, arm the active harness's durable goal mechanism with the full program objective when one is available. The goal continues across turns until the queue is done.
2. **Spawn one owner per PR with the full lifecycle and an early trail.** Resolve the forge once for the program and use it for all PR operations: `gh` by default; use `origin pr ...` only when the `origin` command is available and can resolve this repository, otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Within about 15 minutes, each owner starts an uncommitted `decisions.tsv` trail, pushes its first branch snapshot, and opens the PR ready, never draft. Open the PR before full self-proof so the URL, decisions, and checks form a durable trail. The owner then completes the build, automated-review triage per `../references/bugbot-triage.md`, the available cleanup pass, `.agents/skills/no-comments/SKILL.md`, and the rebase rules below. Keep the trail and return it with the report. Track each spawned agent's ID, expected runtime (at least the longest past run of that kind), and state in an uncommitted `children.tsv`. Rebase once before reporting the code-ready head and starting babysit; keep that merge base during fix rounds. Rebase again during merge prep, or earlier only when `git merge-tree` finds a trunk conflict or CI fails because of a trunk change. When the shipped code is final and cleanup is complete, report the code-ready head SHA; this starts the first verification round before full self-proof. Report the SHA of every later push that changes the patch. In each round, run the owner's real-artifact self-proof (the **prove-it-works** principle skill), CI, and babysit alongside the root's swarm; report owner-ready with the head SHA when all three finish. Before each push that starts a round, run the repository's path-specific pre-review checks on the committed head. A hook pass does not count as proof. Publish each rebase only on the owner's own branch, with `git push --force-with-lease` after an `ls-remote` check. Never force-push a shared branch. The owner may not merge without Step 4's clean verdict.
3. **Run owners in true parallel and never stack.** Many owners at once when PRs are self-contained: one writer per branch, disjoint files, cross-PR drift absorbed by rebase. Only genuinely overlapping work serializes. Independent PRs branch straight off main; sequenced work is merge-then-branch. Do not register or stack independent PRs with Graphite. One exception: an owner that must split a genuinely dependent change may hold a short private stack.
4. **Swarm-verify every code round.** Start a round at the code-ready head SHA and at every later push that changes the patch. Fan out independent verifiers per the **swarm** skill and aggregate one verdict. Re-run the required gates at that SHA, prove the load-bearing behavior live on the real surface with the active harness's browser, desktop, terminal, or service-control capability, and audit the receipts in the owner-ready report plus the diff. Use at least two audit lanes with distinct focuses, such as caller coverage, races, or data and config safety, and give each the full review brief. Run the same behavior on current trunk as a regression check. If trunk cannot perform the new behavior, record that and verify the new behavior and its final user-visible result on the change. The live lane is required for a clean verdict. Send every proven finding to the owner in one fix-forward. A finding reported as a note still counts. For each behavior defect, require a failing test that covers every affected site, or a reproduction receipt when a test cannot show it. Add the defect to the next round's brief. The owner-ready report is not a verdict. The PR is merge-ready only when the root's clean verdict matches that patch and Step 5's post-rebase checks pass; retain a prior lane result only when `playbooks/shipping.md` says its patch-id still applies.
5. **Prepare and merge only the verified patch.** Start merge prep only after the round's lanes have started. Rebase onto current trunk immediately before merging and report the resulting head SHA. CI must pass on that exact head. Compare its base-to-head patch-id with the round's verdict. If trunk moves before the merge, apply `playbooks/shipping.md`. Re-verify when the patch changed, unless that playbook preserves a lane's result for a proven test, docs, or lint-only difference. When the patch did not change, keep the code verdict but rerun mergeability and CI on the current head. Never use a green check from an older SHA as proof. On a clean result, the owner squash-merges its PR and takes the next self-contained item. The operator's full-autonomy grant plus the root's clean verdict authorizes that merge. Operator-named items stop at merge-ready and wait for the operator's click.
6. **Run the root layer.** A genuinely new raise of a pinned gate or budget value (a limit CI only lets tighten) needs your fresh countersign, granted only after verifier proof. If the operator's grant or standing orders cover tool approvals, record that countersign in the format the tool permits and link it to the root's verdict. A lane checks the approval record against the countersign. Never bypass an approval enforced by the forge. Absorbing values that already landed on main is drift, not a raise. Run an audit tick over all owners roughly every 30 minutes. A local root arms each tick through the active harness's recurring loop or monitored-shell mechanism. A remote root uses its recurring wake mechanism. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from trunk with `git show origin/main:.agents/skills/superdev-mode/playbooks/autopilot-full.md`, then re-read the durable goal when the harness exposes one. Audit the operation against both. Fix drift during that tick. Probe each owner, collect decision trails, and inspect every `children.tsv`. Count only side effects as progress: commits, pushes, PR or check deltas, and stored reports. Treat a lane or child that errors or passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement if its work is still needed. Record the stalled child and replacement. If the owner cannot do so, the root handles it. Do not treat a stall as proof or as a reason to drop the work. When merges batch, run a retro pass and a post-merge bot-comment sweep. End the tick after delegated work finishes, including work that remains after the last merge.
7. **Stand down instantly on the operator's stop.** The operator's hold or stand-down reaches every owner as a zero-writes order immediately. Owners hold their briefs until the operator releases them.

**Reply:** the queue with each PR's owner, state, and head SHA. Each verdict and the swarm that produced it. What merged and what each owner took next. Countersigns granted and why. Open operator gates. Where the collected decision trails live.
