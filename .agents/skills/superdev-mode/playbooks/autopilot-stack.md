### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear Graphite stack to review and land.** The sibling of **Autopilot-full**.

1. **Run the owner loop unchanged.** One remote or isolated agent per PR owns its change end to end: build, registration in the repository's stacking workflow, self-proof (gates, CI, receipts), skeptical automated-review triage per `../references/bugbot-triage.md`, the available code-cleanup pass, `.agents/skills/no-comments/SKILL.md`, and babysit to green per `playbooks/babysit.md`. Owners parallelize when the work is self-contained. Every owner keeps a `decisions.tsv` trail per the **show-me-your-work** skill and an uncommitted `children.tsv` with each subagent's ID, expected runtime, and state. Return the decision trail in its report.
2. **Audit on the wake chain.** The root runs an audit tick roughly every 30 minutes. A local root arms each tick through the active harness's recurring loop or monitored-shell mechanism. A remote root uses its recurring wake mechanism. Never leave the cadence to memory or lossy completion notifications. At each tick, re-read this playbook from trunk with `git show origin/main:.agents/skills/superdev-mode/playbooks/autopilot-stack.md`, then re-read the durable goal when the harness exposes one. Audit the operation against both. Fix drift during that tick. Probe each owner and each listed subagent. Count only side effects as progress: commits, pushes, PR or check deltas, and stored reports. Treat a lane or child that errors or passes its expected runtime without a side effect as stuck. Stand it down and dispatch a replacement if its work is still needed, following step 6 of Autopilot-full. Do not wait for a polite return.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On the operator's explicit go, arm the active harness's durable goal mechanism with the full program objective when one is available. The goal continues across turns until the chain is done. On the operator's stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** The owner reports its code-ready head SHA once the shipped code is final, then reports STACK-READY with the exact head SHA when its loop is green. STACK-READY is the owner's signal, not the root's verdict. The root verifies each round per step 4 of Autopilot-full; nothing enters the stack until that independent verdict is clean.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear Graphite stack, in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** Stack mechanics follow Graphite (`gt`), with the division of labor the cloud environment forces. An owner pushes only its own branch, `git push --force-with-lease` after an ls-remote check, and reports its tip and intended parent. The root owns stack topology and registers each append locally: `gt track -p <current-tip>`, then `gt submit --no-interactive --stack` from the tip. `gt submit` walks from trunk, and a cloud agent must never pull branches below its own into that walk; when instructed, it may set its bottom PR's base directly instead.
7. **Absorb drift at the root, then re-verify what moved.** The root absorbs trunk movement by restacking the chain (`gt restack`, `gt sync`); when a restack surfaces conflicts in an owner's files, that owner fixes its own slice and the root pushes the result. A restack rewrites every SHA above it and voids verdicts at the old SHAs. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA. Anything no longer valid goes back through step 4 before delivery. Rerun mergeability and CI after every rewritten push even when the patch-id is unchanged. The countersign rule is unchanged from Autopilot-full. A genuinely new pin raises a stop for the root's fresh countersign. Absorbing drift of landed values is not a raise.
8. **Deliver the chain.** The deliverable is one linear chain of verified PRs, reviewable bottom-up in the Graphite UI, every link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it, with their own clicks or by arming merge-when-ready.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
